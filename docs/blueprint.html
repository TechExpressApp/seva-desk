Architect's choices

Tech stack, and why each piece won

The guiding rule: one developer must be able to build, run and sell this. That favours a modular monolith over microservices, open‑source over licensed, and one cheap VM over a managed‑everything bill.

How the pieces fit

Rules that keep it maintainable

  • Modules talk through published events (DonationRecorded, EventPublished), never through each other's repositories. Spring Modulith tests enforce this.
  • Every table has tenant_id, created_at/by, updated_at/by, soft‑delete flag.
  • One custom_fields JSONB column on Contact, Donation, Booking so temples can add fields without code changes.
  • OpenAPI spec generated by springdoc; the Angular client is generated from it.
  • Testcontainers for real PostgreSQL in integration tests.
The product you can sell

Multi‑tenancy and white‑labelling

A new temple is a row in the tenant table plus a logo upload. No new deployment, no code change. This is what lets you sell to the tenth temple at almost zero extra cost.

Branding (per tenant)

  • Name, short name, logo, favicon, deity or hero image
  • Primary, accent and soft colours → PrimeNG design tokens
  • Greeting line ("Hare Krishna", "Waheguru Ji Ka Khalsa")
  • Receipt header, signature, tax registration number
  • Email sender name and reply‑to

Vocabulary & locale

  • Term overrides: Priest, Seva, Prasadam, Hall, Donation
  • Languages enabled, default language
  • Currency, time zone, date format
  • Fund names (Annadanam, Gau Seva, Building Fund…)
  • Tax rules: 80G (India), 501(c)(3) (US), Gift Aid (UK)

Plan & feature flags

  • Modules switched on per subscription tier
  • Limits: users, contacts, storage, AI chat messages
  • Domain: radhagovinda.sevadesk.app or the temple's own admin.mytemple.org
  • Their own social, email, payment and WhatsApp credentials, encrypted
At startup the Angular app calls GET /api/public/branding. The server resolves the tenant from the Host header and returns colours, logo URL, vocabulary and enabled modules. The app writes the colours into CSS variables and loads the vocabulary into ngx‑translate before the first screen paints. Try the tenant switcher in the Screens section to see the effect.

Outside world

Social media, email, chat and payments

Seamless event posting

One "Publish" button fans out to every connected channel. Posts go through an outbox table, so a Facebook outage doesn't lose the post; a scheduler retries and records the result per channel.

  • Email: Brevo (free tier ~300/day) or Amazon SES; only contacts with consent; unsubscribe link built in.
  • Facebook Page + Instagram: Meta Graph API. Each temple connects its own Page once via "Connect Facebook". Instagram must be a Business account linked to that Page.
  • X / Twitter: API v2 POST /2/tweets. Write access pricing changes often; keep it optional per tenant.
  • Fallback: if a channel isn't connected, show "Copy caption + open site" so staff can post by hand.
  • Design a SocialPublisher interface so YouTube, WhatsApp Channels or Telegram can be added later as adapters.

Chat box with WhatsApp hand‑off

One <script> tag embeds the widget on the temple website and in the admin app.

  • Knowledge base per temple: timings, festival dates, seva prices, guest house rules, directions, FAQs, plus uploaded PDFs. Chunks are embedded into pgvector.
  • Answer: retrieve the best matching chunks, have Claude Haiku answer only from them, show the source.
  • Hand‑off: low confidence, a personal request, or the user taps "Talk to a person" → a WhatsApp button opening wa.me/<number>?text=… with the question pre‑filled. Free, no WhatsApp Business API needed.
  • Unanswered questions are logged so staff can add them to the FAQ.
  • Cost guard: per‑tenant monthly message cap; a free tier that uses Postgres full‑text search only, without the LLM.

Online payments

  • Razorpay (India: UPI, cards, netbanking) and Stripe (US/UK/EU) behind one PaymentGateway interface.
  • Each temple uses its own merchant account, so money never flows through you.
  • Webhook → DonationRecorded event → receipt + dashboard update in seconds.
  • You never store card numbers; the gateway's hosted checkout handles them.

Real‑time reports

  • Every donation or expense publishes an event; the reporting module updates running totals and pushes them over SSE to open dashboards.
  • Totals by day, fund, payment mode, event; donations vs expenses by month.
  • Heavier reports from PostgreSQL materialized views refreshed every few minutes.
  • Export to Excel/PDF; scheduled monthly summary email to trustees.

CI/CD pipeline (GitHub Actions)

  • On every PR: Maven build, unit + Testcontainers tests, Angular lint/test/build, OWASP dependency check.
  • On merge to main: build Docker images (Spring Boot layered jar on eclipse-temurin:21-jre), push to GitHub Container Registry, deploy to staging over SSH with docker compose pull && up -d.
  • On tag v*: manual approval, then the same deploy to production. Flyway migrates the schema on start.
  • Rollback: redeploy the previous tag. Migrations are written backward‑compatible (expand, then contract) so the old version still runs.
  • Custom domains: Caddy's on‑demand TLS asks /internal/domain-allowed before issuing a certificate, so only registered temple domains get one.

Monitoring

  • Spring Actuator + Micrometer → Grafana Cloud free tier (metrics, logs)
  • Uptime check every minute (Uptime Kuma or Better Stack free) with alerts to your phone
  • Sentry for exceptions with tenant tag
  • Disk, backup‑success and certificate‑expiry alerts

Scaling path

  • 1–30 temples: one VM as above.
  • 30–200: managed PostgreSQL (e.g. AWS RDS, DigitalOcean, Neon) + two app VMs behind a load balancer; ShedLock already keeps jobs safe.
  • 200+: containers on ECS/Cloud Run or Kubernetes; split out the chat or social module only if it becomes the bottleneck.
  • Festival peaks (Janmashtami, Diwali): scale the VM up a size for the week; it is a reboot, not a re‑architecture.
Your requirement: weekly backups

Backups and recovery

Weekly is the requirement you gave; I recommend adding a nightly copy because a week of lost donation entries is painful to re‑key. Both are cheap.

Schedule

  • Weekly full backup, Sunday 01:30 local time: pg_dump -Fc, encrypted with age, uploaded to an R2 bucket with object lock. Keep 12 weekly + 12 monthly copies.
  • Nightly backup (recommended): same process, keep 7 days.
  • Files (logos, photos, receipts) already live in R2 with versioning on.
  • VM snapshot weekly from the cloud provider for fast full‑server restore.
  • Monthly restore drill: a job restores the latest backup into staging and runs a row‑count check; failure alerts you.
  • Per‑temple export: any temple admin can download all its data as Excel/JSON. This builds trust when you sell.

Targets: lose at most 24 hours of data (RPO), back online within 2 hours (RTO). Add WAL archiving with pgBackRest later for point‑in‑time recovery.

backup.sh (runs inside the backup container)

#!/bin/sh
set -eu
TS=$(date +%Y-%m-%d_%H%M)
KIND=${1:-weekly}            # weekly | nightly
FILE=/tmp/sevadesk_${KIND}_${TS}.dump.age

pg_dump -h db -U "$PGUSER" -Fc sevadesk \
  | age -r "$BACKUP_PUBKEY" > "$FILE"

rclone copy "$FILE" r2:sevadesk-backups/$KIND/
rm -f "$FILE"

# retention handled by R2 lifecycle rules
curl -fsS "$HEALTHCHECK_URL/$KIND" >/dev/null

# crontab
# 30 1 * * 0  /backup.sh weekly
# 30 2 * * 1-6 /backup.sh nightly

Plan for these early

Watch‑outs

Platform approvals take time

  • Meta (Facebook/Instagram) needs app review and business verification before other temples can connect their Pages. Start in week 10, not week 13.
  • X API write access is paid above a small free quota and the terms change; keep it an optional channel.

Money and trust

  • Receipt numbering must be gap‑free per financial year; use a database sequence per tenant, never "max + 1".
  • Get one chartered accountant to review receipt formats (80G wording, trust registration numbers) before go‑live.

Selling to other temples

  • Write a simple terms of service and data‑processing agreement; temples will ask who owns the donor data (they do).
  • Keep a demo tenant with realistic sample data for sales calls.
  • Brand names and logos belong to each temple; upload only what they provide.

Keeping it a one‑person job

  • Resist per‑temple code branches. Every request becomes a setting, a custom field or a feature flag.
  • Upgrade Spring Boot and Angular twice a year on a fixed calendar.
